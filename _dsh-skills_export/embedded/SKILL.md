# 嵌入式固件任务路由

先判断任务属于哪一类，再加载对应子 skill。不要凭记忆直接改代码。

| 现象 / 任务 | 加载 |
|---|---|
| 新板子第一次上电、外设不工作、时钟或引脚配置 | `mcu-bringup` |
| 死机、HardFault、跑飞、进 Default_Handler、复位循环 | `hardfault-triage` |
| 任务划分、优先级、栈溢出、互斥、死锁 | `rtos-patterns` |
| 编译链接报错、段放错、map 分析、工具链问题 | `linker-and-build` |
| Flash 分区、跳转、IAP、OTA、回滚 | `bootloader-ota` |
| C++ 能不能用、模板或异常或 RTTI 怎么取舍 | `cpp-in-embedded` |
| 想在 PC 上跑固件单元测试、mock HAL | `host-unit-test` |
| 代码规范、volatile、位域、中断安全 | `embedded-c-style` |
| EC 固件、键盘矩阵、电池、SMBus、ACPI | `ec-firmware` |

## 动手前的通用约束

- **不知道芯片型号就先问**。寄存器地址、时钟名、中断号、引脚复用表一律以对应参考手册为准，不猜、不套别的芯片。
- 改动前先确认四件事：工具链版本、优化等级、是否开了 LTO、堆栈大小从哪来。这四项变了，很多"玄学问题"会跟着变。
- 任何"先烧进去看看"之前，先确认回退路径存在（调试器、DFU、备份镜像）。
- 汇编、链接脚本、启动文件属于高风险改动，改完要能逐条说明为什么在。
- 时钟、电源、Flash 时序这类涉及芯片手册数值的，给出结论时标注"需查手册确认"。

## 典型任务的开场动作

1. **板子不工作**：先量供电和复位，再连调试器读复位源，不要急着看代码。
2. **随机死机**：先加故障捕获（记录 CFSR/HFSR 到 RAM 或串口），再谈定位。
3. **性能不达标**：先测真实耗时（GPIO 翻转加示波器，或 DWT 周期计数），不要凭感觉优化。
4. **要写新外设驱动**：先找到手册里的初始化顺序图和数据流，再写寄存器序列。
