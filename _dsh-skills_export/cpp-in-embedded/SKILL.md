# 嵌入式 C++ 取舍

## 先给结论

现代 C++（C++11 起）在 Cortex-M 上完全可用，前提是**关掉异常和 RTTI，且不用动态分配**。收益是类型安全、零开销抽象、编译期计算；代价是要懂哪些特性会偷偷带进运行时代码。

推荐起步配置：

```
-fno-exceptions -fno-rtti -fno-threadsafe-statics -fno-use-cxa-atexit
-std=c++17 -Os
```

## 逐项取舍

| 特性 | 建议 | 原因 |
|---|---|---|
| 异常 | 关 | 代码体积和栈开销大，嵌入式多用错误码 |
| RTTI | 关 | `dynamic_cast`/`typeid` 带进类型信息表 |
| 模板 | 用，但控制实例化数量 | 每个实例一份代码，容易膨胀 |
| constexpr | 大量用 | 编译期算完，运行期零成本 |
| 虚函数 | 慎用 | 每个对象一个 vptr，调用不可内联 |
| 静态多态（CRTP/模板） | 优先 | 零开销，可内联 |
| `new`/`delete` | 默认禁用 | 碎片化，行为不可预测 |
| 全局对象构造 | 慎用 | 静态初始化顺序问题 |

## 静态初始化顺序

- 全局对象的构造函数在 `main` 之前跑，此时时钟、外设、RTOS 都还没初始化。
- 在构造里访问硬件是最常见的翻车点。
- 用"显式 init 函数"代替构造函数做硬件初始化；或者用 `constexpr` 构造 + 运行时 `init()` 两步走。
- `-fno-threadsafe-statics` 能去掉局部静态变量的锁开销，但要求单线程初始化。

## 不用 new/delete 的替代

- 静态池：固定大小数组 + 空闲链表，行为可预测。
- placement new 到预分配缓冲区，配合 `std::span` 之类做视图。
- 需要容器时用 `etl` 这类固定容量实现，不要用 STL 的动态容器。

## 与 C 互操作

- C 头文件要用 `extern "C"` 包起来。
- 中断向量表和启动文件通常是 C 符号，注意名称修饰（mangled name）不会影响 `extern "C"`。
- 回调从 C 调 C++ 时，只能用普通函数指针，不能传成员函数指针；用静态成员函数 + 传 `this` 绕过。

## 体积排查

- 链接后如果出现 `__cxa_throw`、`__gxx_personality_v0`、`typeinfo` 相关符号，说明异常或 RTTI 没关干净。
- 模板实例化过多时，`nm --size-sort` 会看到大量相似符号；把共同部分抽成非模板函数。
- 虚函数表会让对象变大，通信协议结构体里不要放虚函数。

## 判断标准

如果团队里没人能说清"这行代码生成了什么"，就不要引入对应的特性。C++ 在嵌入式是工具，不是目标。
