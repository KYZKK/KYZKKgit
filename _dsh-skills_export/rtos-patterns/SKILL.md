# RTOS 设计与排查

## 任务划分

按"周期 + 阻塞点"划分，不按功能模块划分。

- 每个任务要有明确的周期或事件源，以及一个固定的阻塞点（等队列、等信号量、等延时）。
- 任务数量不是越多越好。能用状态机在一个任务里做完的，不要拆成三个。
- 优先级按截止时间定（rate monotonic）：周期越短、截止越紧，优先级越高。
- 优先级不要超过 5 档，档位多了没人维护得动。

## 栈深度

估算公式：`最深调用链各帧之和 + 最大局部变量 + 中断/上下文保存开销`，再乘 1.3～1.5。

- FreeRTOS 用 `uxTaskGetStackHighWaterMark` 看历史最低水位，跑满一轮业务场景后再定稿。
- 水位低于 20% 就加栈，别等到 STKOF。
- 中断栈是独立的（Cortex-M 上主栈指针），别忘了给中断留够。
- 浮点任务要额外留 FPU 上下文空间。

## 同步原语选择

| 需求 | 用什么 | 注意 |
|---|---|---|
| 任务间传数据 | 队列（拷贝）或流缓冲 | 队列深度按最坏突发量定，不是平均值 |
| 中断通知任务 | 任务通知（FreeRTOS）或信号量 | 比队列轻，但只能一对一 |
| 保护共享资源 | 互斥量（带优先级继承） | 不要用二值信号量代替 |
| 等多个事件 | 事件组 | 注意清除位的时机 |
| 单纯让出 CPU | 任务延时 | 不要用空循环 |

- 互斥量不能在中断里用。
- 中断里只能用 `...FromISR` 版本的 API，且要传 `pxHigherPriorityTaskWoken` 并按返回值决定是否 `portYIELD_FROM_ISR`。

## 优先级反转与死锁

- 优先级反转：低优先级任务持锁被中优先级抢占，高优先级任务被拖住。解法是互斥量开优先级继承（FreeRTOS 的 mutex 默认有）。
- 死锁四条件里最容易踩的是"循环等待"：两个任务以相反顺序拿两把锁。**统一加锁顺序**是最便宜的解法。
- 持锁期间不要调用可能阻塞的 API（包括日志、内存分配、串口发送）。
- 等待一律带超时，超时后打印现场（哪个任务、哪把锁），否则死锁时无从查起。

## 中断与任务通信

- ISR 里只做：读数据、写环形缓冲、发通知，然后立刻返回。
- 高频中断不要用队列逐条发，用环形缓冲加一个"有新数据"的通知。
- 通知会合并，不能当计数用；需要计数就用信号量或计数器。

## 排查顺序

1. CPU 占用：开运行时统计（FreeRTOS 的 `vTaskGetRunTimeStats`），先看谁占着 CPU。
2. 任务饿死：看是不是有同优先级任务在死循环里不让出。
3. 栈溢出：看水位和 `configCHECK_FOR_STACK_OVERFLOW` 的钩子有没有触发。
4. 偶发卡死：抓任务状态快照（各任务当前状态、等待对象、阻塞时长）。
5. 节拍异常：确认 tick 中断优先级是最低的，且没有被长时间临界区挡住。
